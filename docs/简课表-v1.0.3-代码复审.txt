需要优先修复

1. [P1] 子路径原址升级后，已保存的课表显示为空
   位置　src/js/storage.js:19、46
   Edge 实测：在 /school/ 运行 v1.0.2，导入并保存 11 门课。原址换为新 ZIP，点击更新。新版显示「还没有课表数据」并判为首次运行，旧键仍保存全部 11 门课。v1.0.2 在所有路径使用通用键，新版在子路径只读带目录后缀的键。课表、快照、偏好都受到影响。根路径沿用原键。
   建议在新键缺失时提供一次性恢复流程，识别旧数据并保留原件。同域有多个部署时，由用户确认旧课表归属，避免自动复制到每个子路径。用已保存课表的旧安装做原址升级验收。

2. [P1] 不同窗口的修订号检查与保存仍可交错
   位置　src/js/storage.js:76、89、106；tests/review-regressions.test.mjs:113
   现有测试覆盖了 A 已经保存、B 随后提交旧草稿的情况。两窗口先后读取同一个 revision，再各自写回时，读取和写入之间没有跨窗口锁或事务。用存储适配器控制读写顺序，两次调用都返回成功，修订号都从 5 变成 6，一项改动被覆盖。这项结果是确定性交错测试。Web Storage 规范也要求页面代码按没有跨上下文锁的情形设计。
   建议在同一作用域的 Web Lock 内重读、比对、写入，或使用 IndexedDB 的读写事务。所有写入入口共用同一机制，冲突处理仍保留草稿。参考 https://html.spec.whatwg.org/multipage/webstorage.html#introduction 。

3. [P1] 选择「13节模板」可以静默删除已经排好的课程时段
   位置　src/js/app.js:1864、1926；src/js/model.js:647
   Edge 实测：准备 14 节作息和一条第 14 节的晚课，选择「13节模板」并保存。时段数从 1 变为 0，界面提示「作息时间表已保存」。删除末节和切换至 12 节已有引用检查，13 节模板直接替换作息，保存时规整函数跳过超出范围的排课。
   建议在所有作息变更的最终保存入口检查最新课表的规则和例外；有受影响课程时保留草稿，显示课程并提供重排。冲突弹窗的「仅合并作息」也应复用该检查。

恢复、导入和日历问题

4. [P2] 覆盖前快照可能保存的是旧草稿，撤回无法找回真正被覆盖的状态
   位置　src/js/app.js:1628、1635、252；清空流程同见 src/js/app.js:1800
   Edge 双标签测试：B 打开导入预览，A 随后修改并保存学期名称。B 确认导入，出现冲突提示，选择强制覆盖。检查撤回快照，其中缺少 A 刚保存的名称。原因是快照先取 B 的内存状态，再做修订号检查。即使用户在冲突时放弃覆盖，之前的快照也已被改写。
   建议确认最终写入的版本后，使用当时持久化的最新数据生成撤回快照。主数据与快照共同提交或共同失败，取消操作保留原快照。

5. [P2] 「完整备份」恢复会改写课程默认教师、教室和备注
   位置　src/js/importers.js:503、727
   一门课设置默认教师、默认教室和课程备注，第一条规则另设实验教师与实验室，第二条规则留空以继承默认值。经 JSON 覆盖恢复，首条规则的实验教师与实验室成为整门课默认值，课程备注被清空；第二条规则的继承值被写成固定文本。此时现有课次可能看起来一样，但再改默认值或新增时段会得到不同结果。
   建议恢复时从已验证的备份保留课程层字段和规则层的原始覆盖值。展示用的拼接或回退值只用于预览。回归断言应比较恢复前后的业务字段和后续编辑行为。

6. [P2] 合并达到容量上限的课表可能挤掉已有时段
   位置　src/js/importers.js:643、748、803；src/js/model.js:640
   模块实测：原课表有 600 个合法时段，向排在前面的已有课程合并 1 个新时段。预览显示接纳 1 项、跳过 0 项，实际总数仍为 600，原本排在最后一门课的唯一时段从 1 变为 0。导入先追加，最终规整再按遍历次序截断，合并模式也没有覆盖快照。
   建议先保留全部已有记录，再用剩余配额接纳新项；同时检查每门课 40 条及全库 600 条限制。超出的新项在预览中说明，界面的写入数量从最终差异计算。

7. [P2] v1.0.2 已经保存的跨天调课仍不能成对撤回
   位置　src/js/engine.js:323、334；src/js/model.js:709
   用旧版引擎生成一次跨天调课，经过新版恢复，再从原日期点恢复。原日与目标日分别仍有 1 次课。新生成的调课通过 transferGroupId 可以成对撤回，旧记录缺少该字段。
   建议升级时仅对能够唯一确认的旧记录建立关联；有歧义时列出候选补课供用户确认，防止删除独立补课。

8. [P2] 同一份 HTML 再次覆盖导入，日历事件标识全部变化
   位置　src/js/importers.js:739；src/js/ics.js:144
   公开演示 HTML 两次独立覆盖导入，每次生成相同的 156 个课次，两份 .ics 的 UID 交集为 0。解析出的 HTML 时段没有 ruleId，组装课程时每次随机生成新标识。用户更新课表并再次导入日历时，客户端可能将相同课程识别为新事件。
   建议为相同源课程和时段保留稳定身份或匹配已有 ID，同时维持手动新建时段的唯一性。回归应比较两次导入结果的 UID 集合。

9. [P2] 发送端可生成接收端必定拒收的导入码
   位置　src/js/transfer.js:124、144、197；src/js/app.js:1348
   在未压缩兼容路径验证，80 门课、240 个时段的合法 JSON 生成了 81177 字符的导入码，超过接收端 65536 字符限制。界面仍走复制成功流程。压缩路径同样应检查编码前字节数与编码后长度。
   建议生成端采用接收端相同的硬限制。在即将生成无法恢复的导入码时，直接提供 JSON 文件备份。
